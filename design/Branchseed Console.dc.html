SPEC Elements the frontend must contain
MANDATORY — FROM THE BRIEF
  • Upload CT + aorta mask, no manual clicks
  • A branch list that varies in length
  • Unique ID per branch, parent = aorta
  • Ostium, seed, radius and direction in millimetres
  • Visual check: mask, ostia, arrows — 3 cases minimum
  • An empty state when nothing is found
  • Raw JSON, viewable and downloadable
  • Runtime and peak memory per case
BACKEND CONTRACT
  • POST /api/cases — image + mask, returns case_id
  • POST /api/cases/:id/run — settings, returns run_id
  • GET /api/runs/:id/events — live stages and logs
  • GET /api/cases/:id/prediction — the JSON above
  • GET /api/cases/:id/slice?z= — a slice image
  • GET /api/cases/:id/overlay — ostia and arrows
  • GET /api/cases — the case list
  • GET /api/cases/:id/export — all predictions, zipped
WHAT WINS EXTRA POINTS
  • Origin map: every ostium along the aorta at a glance
  • Clock face for where each branch leaves the wall
  • A drawer showing what was rejected, and why
  • Flags for the tricky cases: cropped ends, trunks, second-order vessels
  • A review log kept apart from detection
  • Batch metrics as proof it reproduces
ENV Runs offline, saves locally
ORGANISER ENVIRONMENT

The organisers will use a hidden test set and a standard environment with four CPU cores, 8 GB RAM, no GPU and no internet access. The initial runtime target is an average of no more than 60 seconds per case; the final limit will be confirmed after the organiser baseline is tested.

WHAT THAT MEANS HERE
  • No network calls, no CDN fonts, no remote assets
  • Files and settings stay in the browser: IndexedDB for volumes, localStorage for settings
  • Every run reports time and peak memory against 60 s and 8 GB
  • Detection still runs in the local Python worker, not the browser
